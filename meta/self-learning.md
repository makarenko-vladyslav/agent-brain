# Self-Learning Protocol

Цей протокол описує як AI-агент вчиться з досвіду і адаптується.

---

## 1. Тригери навчання

### A. Корекція юзера (Negative Feedback)
**Коли:** юзер каже "не так", "стоп", "завжди X", "ніколи Y", "запам'ятай"

**Дія:**
1. Визнач ЩО пішло не так і ЧОМУ
2. Перевір `brain/rules/` — чи є вже правило по цьому
3. Якщо є → оновити, уточнити Why та How to apply
4. Якщо немає → створити нове правило:
   ```markdown
   # Назва правила
   ## Правило — що робити/не робити
   ## Why — причина (інцидент, перевага юзера)
   ## How to apply — коли/де це застосовувати
   ```
5. Commit: `brain: add/update rule — <суть>`

### B. Підтвердження (Positive Feedback)
**Коли:** юзер каже "саме так", "ідеально", приймає без pushback нестандартний підхід

**Дія:**
1. Визнач який підхід спрацював
2. Якщо це НЕ очевидний підхід → зафіксуй як validated approach
3. Це calibration — не тільки помилки навчають, але й успіхи

### C. Новий домен без скіла
**Коли:** задача не покривається жодним існуючим скілом

**Дія:**
1. Виконати задачу з контексту
2. Після завершення → Skill Forge (див. `meta/skill-forge.md`)
3. Зафіксувати новий скіл для майбутнього

### D. Зміна стеку/процесу
**Коли:** юзер мігрує технологію, змінює workflow, або каже "тепер ми робимо інакше"

**Дія:**
1. Оновити `brain/profile.md` (стек)
2. Оновити відповідні `brain/rules/` (процес)
3. Перевірити відповідні `skills/` — чи потрібне оновлення
4. Видалити застарілу інформацію (не закоментувати — ВИДАЛИТИ)

---

## 2. Post-Task Reflection

Після завершення значного блоку роботи, перевір:

| Питання | Дія якщо ТАК |
|---|---|
| З'явились нові знання про домен? | Оновити відповідний скіл |
| Зламався підхід і шукав альтернативу? | Оновити rules/ або скіл |
| Задача була без скіла і повторюватиметься? | Створити новий скіл |
| Юзер дав feedback що варто зберегти? | Оновити rules/ |
| Змінився стек або процес? | Оновити profile.md |

---

## 3. Гігієна знань

### Що зберігати
- Правила роботи (feedback від юзера)
- Профіль та преференції юзера
- Патерни що повторюються
- Validated approaches

### Що НЕ зберігати
- Конкретні баг-фікси (вони в git history)
- Тимчасовий стан задач (вони в GitHub Issues)
- Архітектуру коду (вона в самому коді)
- Щось що вже є в CLAUDE.md проєкту

### Правило дедуплікації
Перед створенням нового запису — ЗАВЖДИ перевірити чи немає існуючого. Краще оновити існуючий ніж створити дублікат. Суперечності між правилами = баг в мозку, негайно виправити.
