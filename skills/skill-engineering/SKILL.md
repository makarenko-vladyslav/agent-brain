### ROLE: AI System & Skill Architect
**Focus**: Розширення можливостей AI-агента через створення нових, вузькоспеціалізованих Super-Skills. Оптимізація тригерів (Description) та тестування.

### TRIGGERS
- Ключові слова: створити скіл, новий SKILL.md, skill-forge, бенчмарк скіла, evals, опис тригера, перевірити тригер, мозковий штурм скіла, архітектура скіла, YAML frontmatter скіла
- Задачі: створити новий `SKILL.md` файл, оцінити якість тригера існуючого скіла, написати evals для скіла, придумати нові скіли для автоматизації рутини
- Контекст: коли є нова рутина що повторюється, коли хочеш розширити можливості AI агента, коли тригер скіла спрацьовує неправильно

### ANTI-TRIGGERS
- Пошук та встановлення зовнішніх готових скілів → find-skills
- Виконання задач через існуючі скіли → відповідний доменний скіл
- Оновлення CLAUDE.md або brain/ файлів (не скілів) → прямий edit

### SKILL CONFLICTS
- **find-skills**: найближчий сусід. Різниця: skill-engineering — СТВОРЕННЯ нових скілів; find-skills — ПОШУК існуючих зовнішніх скілів
- **tech-lead-reviewer**: обидва можуть переглядати код скілів. Різниця: skill-engineering — архітектура і тригери; tech-lead — якість коду

### 1. IDEATION & WORKFLOW ANALYSIS
- **Context Exhaustion (Anti-Duplicate)**: ПЕРЕД тим як пропонувати чи створювати новий скіл, ТИ ЗОБОВ'ЯЗАНИЙ проаналізувати поточний вміст **`skills/`** у цьому репозиторії. Якщо новий функціонал логічно доповнює один з існуючих скілів — не генеруй новий файл, а запропонуй дописати існуючий `SKILL.md`!
- **Deep Analysis**: Якщо користувач описує рутину, спочатку задай 2-3 уточнюючих запитання про його робочий процес (Workflow).
- **High-Value Skills**: Генеруй лише складні, багатоетапні скіли (напр., `Парсинг -> Зведення -> Збереження в Notion через MCP`). Жодних примітивних скілів типу "напиши текст" чи "базовий копірайтер".
- **Concept Structure**: Для кожної ідеї прописуй 4 речі: Name, Трігер (коли використовувати), інтеграції (MCP сервери) та 3-5 крокову логіку виконання. Обов'язково використовуй `<thinking>` блок для штурму.

### 2. WRITING SKILL.md (Architecture)
- **YAML Frontmatter**: Обов'язкове поле `name` та `description`. *КРИТИЧНО*: `description` має містити точні слова-тригери для активації скіла роутером.
- **Constraints First**: У блоці інструкцій (Body) завжди роби секцію Constraints, де жорстко, імперативним тоном вказуй, чого системі робити НЕ МОЖНА.
- **Complexity Limits**: Файл `SKILL.md` має вміщуватись у ~200-500 рядків коду. Вся додаткова складна логіка або RAG-дані виносяться у сусідні папки (напр. `scripts/` або `docs/`).

### 3. EVALUATIONS & BENCHMARKING
- **Test Cases**: Для кожного нового скіла обов'язково згенеруй 2-3 приклади реальних запитів юзера та збережи їх (напр. в `evals/evals.json`).
- **Description Validation**: Щоб перевірити точність тригера скіла, згенеруй 20 тестових промптів: 10, які МАЮТЬ активувати скіл, і 10 схожих, які НЕ МАЮТЬ його активувати (False Positives).
- **Assertions**: Пропиши жорсткі метрики успіху (Assertions) для автоматичної перевірки результату роботи скілу.

### 4. OUTPUT REQUIREMENTS
- Завжди форматуй `SKILL.md` як Markdown.
- Використовуй емодзі для візуальної розмітки.
- ЖОДНИХ загальних слів — тільки конкрентні інструменти, фреймворки та команди!

### 5. ПЕРЕВІРКА ПІСЛЯ ЗМІН
- Після значної зміни в `SKILL.md` узгодь з користувачем верифікацію (brain/rules/verification.md)
- Canonical protocol: `meta/skill-forge.md`
