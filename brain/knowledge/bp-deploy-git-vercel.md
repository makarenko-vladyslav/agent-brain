# Стандартний шлях: усе через git і Vercel

> Один спосіб для всіх проєктів власника-новачка: код у git, сайт на Vercel, домен спрямований туди. Безкоштовно, HTTPS сам, кожна зміна виїжджає автоматично, відкат — один клік. Не пропонуй FTP і «залити файли» — це крок назад.

Це шлях за замовчуванням. Відступати від нього тільки тоді, коли задача його справді не тримає (потрібен постійний сервер, важкі фонові процеси, специфічне ПЗ).

---

## Чому саме так, коли власник не програміст

- **Немає ручної заливки.** Змінив файл → `git push` → за хвилину сайт оновився. Забути щось залити неможливо.
- **HTTPS і сертифікати** Vercel робить сам. На звичайному хостингу це окремий крок, який забувають.
- **Відкат за один клік.** Зламалось — повертаєш попередню версію з панелі. Це рятує людину, яка не вміє лагодити.
- **Кожна версія збережена.** Історія git означає, що нічого не втрачається назавжди.
- **Безкоштовно** для такого масштабу.

## Порядок, який агент виконує сам

1. **Git у проєкті.** `git init`, `.gitignore` (обовʼязково `node_modules`, `.env`, `.next`). Комітити осмислено, не «update».
2. **Репозиторій на GitHub.** Приватний, якщо власник не сказав інакше. Створити через `gh repo create` — не просити власника робити це в браузері.
3. **Підключити Vercel до репозиторію.** Далі кожен `git push` = автоматичний деплой.
4. **Перевірити самому** — відкрити видану адресу й подивитись, що працює саме те, що треба.
5. **Домен.** У Vercel додати домен, він покаже DNS-записи; вписати їх у панелі реєстратора домену. HTTPS увімкнеться сам.
6. **Сказати власнику простими словами**, що сайт живий, за якою адресою, і що далі зміни виїжджають самі.

## Що потрібно від власника — і тільки це

Реєстрація на Vercel і GitHub (акаунти створює він сам, агент не реєструє за нього) · доступ до панелі реєстратора домену, щоб вписати DNS · рішення, чи репозиторій приватний.

## Як пояснювати git власнику, який у ньому не розбирається

Не термінами, а суттю: **git — це історія збережень.** Кожен коміт — точка, у яку можна повернутись. Push — «відправити зміни, щоб сайт оновився».

Йому не треба знати ні гілок, ні merge. Агент робить це сам і каже результат: «зміни на сайті, попередня версія збережена».

## Домен: чого чекати

Після зміни DNS домен запрацює не миттєво — від кількох хвилин до кількох годин. **Попередити наперед**, інакше власник вирішить, що зламалось. Перевіряти `dig +short домен`, а не оновлювати браузер по колу.

## Якщо хостинг уже куплений

Буває, що людина встигла купити звичайний хостинг, перш ніж спитала. Тоді:

- **Домен точно знадобиться** — його спрямовуємо на Vercel, гроші не пропали.
- **Хостинг для цієї задачі не потрібен.** Сказати прямо, але без докорів: «сайт житиме на безкоштовному Vercel, це надійніше й простіше; хостинг лишиться про запас або на нього можна поставити пошту».
- Якщо власник наполягає використати оплачене — статику залити можна (тека `public_html`, увімкнути SSL у панелі), але кожне оновлення стане ручним, і про це треба сказати чесно.

## Найчастіші граблі

- **`.env` потрапив у git** — секрети стали публічними. Перевіряти `.gitignore` **до** першого коміту.
- **`node_modules` у репозиторії** — сотні мегабайт сміття.
- Next.js із серверними функціями намагаються залити на звичайний хостинг — не запуститься.
- Домен доданий у Vercel, але DNS не змінений — сайт відкривається лише за адресою Vercel.
- Забули, що зміни треба **комітити й пушити**, а не просто зберегти файл.
