# Нічний агент-інженер (проєкт) — як зроблено і чому
> Нічний агент проєкт: чому прибиральник сміття став інженером, чому промпт не сміє суперечити сам собі, які гейти й межі змін.

**Дата:** 29.07.2026. Еволюція `.omc/scripts/nightly-deslop.sh` з «прибиральника сміття» в інженера нічної зміни.

## Що змінилось у ролі

Було: видаляти мертвий код, дублювання, зайві абстракції.
Стало (за вимогою власника): **шукати дефекти → доробляти напівзроблене → переписувати поганий код → і лише потім прибирати залишки**. Прибирання опустилось із першого пункту на п'ятий.

Причина зміни: агент видалив «мертвий код», який насправді був **заготовками недороблених фіч** (визначення робочих годин, очікування аналізу конкурентів). Відсутність споживача ≠ мертвий код.

## Патерни, що виявились суттєвими

### 1. Промпт не має суперечити сам собі
Перша версія розширеної ролі казала «шукай і лагодь дефекти», а старе правило нижче — «не змінюй runtime behavior». Виправлення бага **за визначенням** змінює поведінку в зламаному випадку. Агент із такою суперечністю за замовчуванням не робить нічого.

Формулювання, що працює: заборонено міняти **задуману** поведінку й **форму** публічного API; виправляти дефект — можна й треба, але лише коли тест доводить, що стара поведінка була хибною.

### 2. «Доводити, а не заявляти» — прямо в промпті
Секція `PROOF, NOT CLAIMS`: жодних «готово» без виводу команди; кожна зміна отримує тест, який **червонів би без неї**; думати з боку критика / навантаження / нещасливого шляху; недоведене — в окрему секцію `NOT PROVEN:`.

Структурований звіт (`FIXED / FINISHED / REWRITTEN / REMOVED / SCAFFOLDING LEFT UNTOUCHED / FOUND, NOT FIXED / NOT PROVEN`) робить нечесність помітною: порожня секція `NOT PROVEN` при купі змін — сама по собі сигнал.

### 3. Знахідки мають виходити з логів у трекер
`FOUND, NOT FIXED:` парситься і стає GitHub issue. Без цього розділ звіту читає лише той, хто відкриє лог, — тобто ніхто.

### 4. GitHub API — eventually consistent, дедуп на ньому не будується
`gh issue list` **не бачить щойно створений issue** і **показує щойно закритий** як відкритий. Перевірено: три прогони поспіль створили три дублікати. `--search` ще гірший — окремий пошуковий індекс із хвилинним лагом.

Робоче рішення: **локальний реєстр** `модуль → номер issue` у файлі. Перевірка стану — `gh issue view <N>` (читання **за номером** консистентне, на відміну від списку).

### 5. Мітки мають існувати
`gh issue create --label "[Інфра]"` падає, якщо мітки немає. `[Інфра]` у цьому репо — конвенція **префікса заголовка**, не мітка. Перевіряти `gh label list` перед тим, як покладатись на мітку.

### 6. Мовчазні `2>/dev/null` ховають саме те, що ламає ніч
Запис реєстру падав з `KeyError`, бо змінна оболонки не була експортована, а `2>/dev/null` це ковтав — і дедуп мовчки не працював. Передавати дані **аргументами**, а не через env; на критичних кроках не глушити stderr.

### 7. Знати межу свого вікна
Headless `claude` **не продовжує OAuth-токен** (перевірено: `expiresAt` не змінюється після виклику). Тому модуль, стартований за 30 хв до спливу, помре посеред роботи, впаде на гейті й буде позначений `failed` — з хибним висновком «модуль складний» у файлі уроків.

Рішення: перед стартом модуля звіряти залишок токена з порогом, що покриває повний цикл (агент + 4 гейти + push), і охайно завершувати ніч.

### 8. Парсити вивід агента — за форматом, у якому він РЕАЛЬНО пише

Промпт просив секцію `FOUND, NOT FIXED:`. Агент, як і будь-яка модель, пише markdown: `## FOUND, NOT FIXED`. Регекс вимагав рядок, що **починається** з `FOUND` — і не збігався ніколи.

Наслідок: перша бойова ніч знайшла **шість реальних дефектів** (серед них розходження гейтів доступу, через яке адміністратор з іншою поштою читав усі промпти й суми витрат через API, і кнопка, що безповоротно стирала всю історію витрат без підтвердження) — і **жодного issue не завела**. Знахідки лежали в лог-файлі й зникли б.

Правило: парсер має приймати `## ЗАГОЛОВОК`, `**ЗАГОЛОВОК:**` і голий текст. І перевірятися **на справжньому виводі агента**, а не на прикладі, який сам же й вигадав — вигаданий приклад підтверджує лише те, що регекс збігається сам із собою.

### 9. Не тримати єдиний слот під вивід кількох агентів

Другий агент (прохід на покриття) писав у той самий файл, що й перший, і затирав звіт основного — з усією аргументацією діфа. Наступного ранку діагностувати не було чим. Кожен виклик має лишати іменовану копію.

### 10. Лічильник, який мовчки бреше, дорожчий за відсутній

`git diff --numstat` не показує **нових** файлів. Агент створював тести саме як нові файли — лічильник бачив нуль, механізм «нема тестів → додатковий прохід» бив тричі даремно, спалив три Opus-сесії й записав три брехливі уроки, які отруїли б наступні ночі. Рахувати зміни треба після `git add` (по індексу).

Побічний ефект цього ж `git add`: застейджений файл робить `git checkout -- <шлях>` **безпечним для зловмисної зміни** — відновлення йде з індексу, тобто повертає саме те, що мало бути скасоване. Захист має спершу знімати зі стейджа, потім відновлювати з `HEAD`.

## Загальний висновок

Автономний агент ламається не на складному коді, а на **інфраструктурних припущеннях**: що API віддає свіжі дані, що мітка існує, що змінна експортована, що креденшел доживе до кінця. Кожне з них треба **перевіряти живцем**, а не припускати.
