# Зміни, що впливають на інших агентів — оголошувати проактивно

## Правило
Коли щось **додається / змінюється / прибирається** і це може вплинути на роботу
інших агентів (автоматизація, фонові процеси, розклади, нові worktree, спільні
файли, конвенції, воркфлоу, інфраструктура) — ЗАВЖДИ зробити так, щоб інші агенти
про це дізналися й враховували. Не мовчати, не покладатися на те, що «побачать
самі».

## Як застосовувати
1. Писати в канали, які **кожен агент читає при старті сесії**: `CLAUDE.md`
   (Claude Code) + `AGENTS.md` (codex / OMC / Cursor). Це головний механізм —
   НЕ auto-memory і НЕ README (їх не кожен агент відкриває).
2. Секцію ставити помітно (верх файлу), у трьох частинах:
   - **Факт** — що з'явилося / змінилося / зникло.
   - **Як перевірити стан** — конкретні команди/чекліст «перед тим як щось робити».
   - **Правила співіснування** — чого не робити, що чекати, як не зіткнутися.
3. Пам'ятати межу поширення: CLAUDE.md/AGENTS.md вантажаться раз на старті → нові
   сесії бачать автоматично; вже-запущені сесії та інші worktree — лише після
   рестарту або `git pull`. Тож зміну доків треба **закомітити+запушити** (коли
   спільна гілка вільна), а не лишати тільки локально.
4. Якщо доречно — продублювати факт у project-memory для власного відновлення
   контексту, але це вторинне до CLAUDE.md/AGENTS.md.

## Чому
Проєкти часто ведуть кілька паралельних агентів одночасно (cmux).
Якщо один змінює щось спільне, а решта не знають — race conditions, дубляж роботи,
затерті зміни, конфлікти при merge/push. Юзер прямо вимагає проактивну
координацію: «зроби щоб всі агенти про це знали і враховували, перевіряли стан
перед тим як щось робити». (Джерело: робоча сесія 2026-07 — налаштування нічного
авто-деслопу, що пушить у staging.)

## Сфера
**ВСІ проєкти, назавжди.** Будь-яка мультиагентна робота.
